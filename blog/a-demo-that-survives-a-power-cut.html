A demo that survives a power cut

Science fairs have bad Wi-Fi, flat batteries and a queue. The demo that wins is the one that still works when all three happen.

Published 7 November 20263 min readBy a student, for students

01Assume every connection will fail

Not out of pessimism — because it is the normal case. A school hall has hundreds of phones on one access point, the projector laptop is doing something else, and the queue means you will demo the same thing eleven times. Anything that needs a live network to be interesting will be uninteresting at least twice that day.

So the design rule is simple: the important part of the demo must work with the network off. Everything that needs a connection is a bonus you can mention, not a step you depend on.

02Test it the way it will fail

An honest test takes four minutes and you should do it the morning of the fair:

  1. Load the whole thing once with the network on.
  2. Turn aeroplane mode on. Do not close the tab.
  3. Reload the page. It should come back.
  4. Do the three things you plan to show, in order, timing each one.

If step three fails, you have found the problem while there is still time to fix it. If step four takes longer than ninety seconds, cut a step — a demo that finishes leaves a better impression than one that is impressive for four minutes.

03Have a paper version of the important screen

One page, printed, that shows what the tool does with a worked example: the question, the answer, the citation. If the phone dies, the laptop will not boot, or the room is too bright, you hand over the page and keep talking. It costs one sheet and it has saved more demos than any backup battery.

Print two. One to keep, one to give away, with your test steps on it so the judge can try it later without you standing there.

04Make the demo something the judge does

The strongest version of any demo is the one where the judge's hands are on it. Hand them the phone with a question already typed, or ask them to pick a page and then ask about something on it. When they produce the question, they cannot suspect you of rehearsing the answer.

Which means the tool has to be obvious in ten seconds, with no setup and no account. If a demo needs a login before it shows anything, practise the login until it is four taps, and have a second device already signed in.

05What to say about the parts that need the internet

Be specific and calm: The web search needs a connection; the cited answers do not. If the Wi-Fi is bad I will show you the offline part, and you can check the search yourself later.

That sentence does two things. It removes the pressure to make the network work, and it tells the judge you know exactly which half of your own system is which — which is the thing a project demo is really testing. A student who says "it usually works" is a student who has not tested it. A student who says "this part needs Wi-Fi, that part does not" has.

This project was built around that sentence: the cited answers, quizzes, flashcards, exam practice, the code reader and the viva all run on the device, and only the labelled web fallback needs the network. There is a whole page of tests a judge can re-run, including one that installs the app, switches the network off and asks for every file — because a claim about offline is worth nothing until somebody has pulled the plug.

How you know it worked

You will know it worked when you demo with aeroplane mode on and the judge does not notice anything is missing.
